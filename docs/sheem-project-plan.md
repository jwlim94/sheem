# Sheem (쉼) — Project Plan

> "쉼" — 한국어로 휴식, 잠시 멈춤. 자연의 소리와 3D 공간이 만나는 힐링 소셜 플랫폼.

> **최종 갱신: 2026-08-24** — 시점/캐릭터/제작 역할 분리 결정 반영, 레포 정리 완료

---

## 1. 프로젝트 개요

### 컨셉
고퀄리티 ASMR 자연음을 3D 공간에서 경험하는 멀티유저 웹 플랫폼. 유저는 3D 맵을 돌아다니며 위치에 따라 달라지는 소리를 경험하고, 같은 소리를 좋아하는 사람들과 자연스럽게 모여 채팅하거나 조용히 공존할 수 있다.

### 핵심 가치
- **공간적 오디오**: 같은 빗소리라도 어디서 듣느냐에 따라 다르게 들린다 (텐트 안, 숲속, 차 안, 처마 밑, 아스팔트 위)
- **소셜 레이어**: 같은 소리를 좋아하는 사람들이 자연스럽게 같은 공간에 모임
- **감성 기반 집중 공간**: 공부, 작업, 휴식을 위한 ambient 환경

### 시각적 목표
젤다 BotW 수준의 스타일라이즈드 룩을 **웹 브라우저에서** 구현.

> ⚠️ 중요한 전제: BotW는 레이트레이싱을 쓰지 않는다. Wii U 실시간 렌더링이다.
> 저 룩을 만드는 건 오프라인 렌더 품질이 아니라 **아트 디렉션 + 라이팅 + 대기감**이다.
> 따라서 목표를 "Blender Cycles 품질"이 아니라 **"젤다 룩"**으로 잡으면 웹에서 도달 가능하다.

젤다 룩을 구성하는 4요소:
1. **대기 원근(aerial perspective)** — 먼 지형이 뿌옇고 푸르스름해지는 것. 체감상 절반이 이것
2. **스타일라이즈드 셰이딩** — 순수 cel-shading이 아닌 부드러운 확산광 + 은은한 rim light
3. **부드러운 그림자 + bloom**
4. **높은 채도, 낮은 대비의 색 그레이딩** (tone mapping)

### 브랜드명
- **영문**: Sheem
- **어원**: 한국어 "쉼" (휴식, 멈춤)
- **발음**: 영어권에서 자연스럽게 읽히면서도 부드럽고 조용한 어감. "Shh-"로 시작하는 소리 자체가 앱 컨셉과 일치

## 3. 기술 스택

### 렌더링 / 3D
- **Three.js + React Three Fiber** — 웹 3D 엔진 (환경, 지형, 셰이더, 카메라)
- **WebGL Shaders (GLSL)** — 날씨, 물, 안개, 대기 원근, 빛 효과
- **Post-processing** — bloom, 색 그레이딩 (젤다 룩의 마지막 한 끗)

### 오디오
- **Web Audio API** — 오디오 처리, 믹싱, 크로스페이드
- **Three.js Audio + AudioListener** — 3D 공간 기반 소리
  - drei의 `<PositionalAudio>`가 아니라 Three.js Audio API 직접 사용 (리스너 위치를 카메라에서 떼어내야 하므로)

### 멀티유저
- **미정** — Colyseus vs Socket.io
  - 이전 스캐폴딩(`server/`)은 Colyseus 기반이었으나 빈 스텁이라 2026-08-24 제거
  - `colyseus.js` 의존성만 package.json에 남아 있음. 결정 시 정리

### 에셋
- **코드 생성**: 지형(미정), 하늘, 날씨, 안개, 대기 원근, 물, 빛, 그림자, 풀·비 파티클
- **Blender**: 건물, 계단, 소품(텐트·벤치), 바위/절벽, 나무 한 그루의 형태
- **자체 제작(Blender)**: 캐릭터 + 의상
  - 완성 전까지 Quaternius Ultimate Animated Character Pack을 프록시로 사용

## 4. 오디오 시스템 설계

### 두 가지 레이어 조합

```
Zone 기반 (배경음)         +    PositionalAudio (오브젝트 기반)
─────────────────────────────────────────────────────────────
숲 구역 배경 빗소리 (낮게)       나뭇잎 위 빗소리 (나무 위치)
                                 웅덩이 빗소리 (웅덩이 위치)
텐트 구역 배경음 (실내감)        텐트 천막 소리 (텐트 위치)
```

- **Zone 전환**: 구역 경계에서 두 소리가 자연스럽게 크로스페이드
- **Positional**: 오브젝트 가까이 갈수록 해당 소리 커짐
- **Ducking**: 플레이어가 음원에 접근하면 배경음이 자동으로 줄어듦 (구현 완료)

### 리스너 설계 (3인칭 전용 문제)

3인칭에서는 카메라가 캐릭터 뒤 3~5m에 있어서, 리스너를 어디에 두느냐가 실제로 소리를 바꾼다.

```
위치(position)     →  캐릭터    "여기 서면 이 소리"라는 제품 핵심을 지키기 위해
방향(orientation)  →  카메라    화면 왼쪽에 보이는 음원이 왼쪽 귀에 들리도록
```

- 카메라 기준 위치면: 캐릭터는 처마 밑인데 리스너는 3~5m 뒤 골목에 있음 → 컨셉이 깨짐
- 캐릭터 기준 방향이면: 캐릭터가 화면에서 왼쪽을 볼 때 소리 좌우가 뒤집힘 → 멀미

**현재 상태**: 위치는 구현 완료(`src/playground/playerState.ts` + `SpatialAudio.tsx`의 `AudioListenerProvider`).
**방향은 미구현** — 리스너 회전이 월드 기본값에 고정되어 있어 카메라를 돌리면 좌우 패닝이 어긋난다.

### 오디오 소싱
- Freesound.org, Pixabay 등에서 고퀄리티 자연음 수집
- **FFmpeg EBU R128 (-16 LUFS) 정규화**로 파일 간 볼륨 통일 (필수 — 안 하면 존 전환 때 볼륨이 튐)
- 현재 6종 확보: rain-heavy, rain-inside-car, rain-on-tent-in-forest, rain-on-tin-roof, rain-on-window-glass, thunder

## 5. 3D 제작 역할 분리

### 핵심 프레임 — 3분할

"고정 vs 실시간"보다 이 축이 실무에서 정확하다:

```
분위기(Atmosphere)  →  코드     빛, 안개, 대기 원근, 색감, 비, 물결
만들기(Authoring)   →  Blender  물체 하나의 "형태"
배치(Placement)     →  코드     그 물체를 어디에 몇 개
```

**만들기와 배치가 갈린다**는 점이 중요하다. 나무는 Blender로 한 그루 만들고, 숲으로 100그루 세우는 건
코드 인스턴싱이다. 100그루를 Blender에서 배치해 통째로 내보내면 파일도 무겁고 draw call도 터진다.

### 항목별 담당

| 영역 | 담당 | 비고 |
|------|------|------|
| 안개 / 대기 원근 | **코드** | Blender가 구조적으로 불가 — 카메라 거리 기반 픽셀 계산 |
| 하늘 | 코드 또는 Blender HDRI | 시간대를 바꿀 거면 코드 |
| 비 / 물결 | **코드** | 매 프레임 변함 |
| 톤매핑 / bloom / 색감 | **코드** | 렌더러·포스트프로세싱 단계 |
| 풀 | **코드** | 수만 개 → InstancedMesh + 바람 vertex shader |
| 건물 / 계단 / 소품 / 바위 | **Blender** | 사람이 의도한 형태 |
| 나무 | Blender(형태) + 코드(배치) | |
| 캐릭터 | **Blender (자체 제작)** | 리깅·애니메이션까지 직접. 완성 전까지 구매 에셋을 프록시로 |
| 캐릭터 의상/소품 | Blender (베이스 리그 기반) | 커스터마이징 2단계 이후 |
| **지형** | **미정** | 아래 참고 |

### 지형 — 아직 결정 안 됨

| | Blender 스컬프팅 | 코드 절차 생성 |
|---|---|---|
| 아트 컨트롤 | 언덕 하나하나 의도대로 | "그럴듯"하지만 특정 형태 지정 어려움 |
| 파일 크기 | MB 단위 | 코드 몇 KB |
| 규모 | 만든 만큼만 | 사실상 무한 |
| 수정 | Blender 열고 재익스포트 | 슬라이더 실시간 |
| **충돌 판정** | 메시 그대로 사용 (쉬움) | 셰이더가 GPU에서 변형 → CPU가 높이를 모름 (어려움) |
| 조명 베이크 | 가능 → Cycles 품질 | 불가 |

> **이전 계획 재검토 필요**: 초기 플랜은 "지형 전체를 slowroads.io처럼 절차적 생성"이었으나,
> slowroads는 **끝없이 달리는 게임**이라 무한 생성이 본질이었다. Sheem은 정반대로 **"머무는 공간"**이고,
> 목표로 삼은 젤다 스크린샷도 무한 지형이 아니라 **의도적으로 배치된 아늑한 마을**이다.
> 한 존이 50m×50m짜리 손으로 디자인한 공간이라면 Blender 스컬프팅이 절차적 생성보다 낫다.

**결정 방법**: 코드 지형에 톤매핑·안개·대기 원근을 얹어보고 "코드만으로 어디까지 되는지"를 눈으로 확인한 뒤 판단.
어느 쪽을 택하든 라이팅·톤매핑 작업은 그대로 쓰이므로 버려지는 게 없다.

### Blender 품질은 그대로 넘어오지 않는다

| Blender 화면에서 보이는 것 | 웹으로 넘어오나 |
|---|---|
| 형태 (지오메트리) | ✅ 예산 안에서 100% |
| 베이스 컬러 / 노멀 텍스처 | ✅ |
| Cycles 간접광·부드러운 그림자·AO | ⚠️ 베이크하면 "그림으로"만 |
| 실시간 반사·굴절 | ❌ |
| 볼류메트릭 빛줄기·안개 | ❌ |
| 디스플레이스먼트 | ❌ (실제 적용 시 폴리곤 폭발) |

Cycles는 한 프레임에 수 초~수 분 쓰는 오프라인 렌더러, 브라우저는 **16ms** 안에 끝내야 한다.
**모델링/텍스처 퀄리티는 그대로 오지만 "빛"은 오지 않는다.**

예산 차이:

| | Blender | 웹 |
|---|---|---|
| 폴리곤 | 수백만 개 무리 없음 | 씬 전체 수십만이 현실선 |
| 텍스처 | 4K 수십 장 | 초기 로드 총합 10~20MB (Sheem은 오디오까지 있어 더 빡셈) |

### 베이킹의 함정 — 인스턴싱과 양립 불가

베이킹은 각 오브젝트가 **고유 UV에 고유한 조명을 그려 넣는 것**이다. 같은 나무 100그루를 베이크하면
텍스처 100장이 필요하고, 반대로 인스턴싱으로 1 draw call에 그리면 조명을 구울 수 없다.

Journey의 포탈 씬이 4 draw call로 끝난 건 씬이 작고 오브젝트가 전부 고유했기 때문이다.
반복 요소가 많은 마을 씬은 성격이 다르다.

**실무 답 — 하이브리드**:
- 크고 고유한 구조물 (집, 지형, 절벽) → 베이크
- 반복되는 것 (풀, 나무, 통, 빨래줄) → 인스턴싱 + 실시간 조명
- 움직이는 것 (캐릭터, 비) → 실시간

## 6. 캐릭터

### 확정 사항
- **인간형** (슬라임 안은 폐기 — 의상 판매 불가)
- **자체 제작.** 모델링부터 리깅·애니메이션·의상까지 직접 만든다
- 완성 전까지는 Quaternius Ultimate Animated Character Pack을 **프록시**로 사용
  (`public/models/`: Knight_Golden_Male, Viking_Male, Wizard, Worker_Male)
- **키를 먼저 확정한다** (예: 1.7m). 이 숫자가 맵의 모든 치수의 기준이 된다
  - 문 2m / 계단 한 칸 18cm / 처마 2.4m / 벤치 45cm — 전부 캐릭터 키에서 파생

### 제작 경로

```
A. 컨셉        등신 비율 결정 + 정면/측면 스케치
B. 모델링      박스 모델링 (미러 모디파이어로 반쪽만) — 5k~15k triangles
               ★ 토폴로지: 어깨·팔꿈치·무릎·손목에 엣지 루프 충분히
C. UV + 텍스처  Seam → Unwrap → 페인팅 (스타일라이즈드면 색면 위주라 수월)
D. 리깅        Armature + Weight Painting          ← 최대 난관
E. 애니메이션   Idle, Walk 최소 2개
F. 익스포트     glTF 2.0, +Y Up, Apply Modifiers
```

**난관 우회 도구 (직접 제작을 훼손하지 않음)**
- **Rigify** (Blender 내장 애드온): 메타리그를 몸에 맞추면 인간형 리그를 자동 생성.
  웨이트도 자동 배분부터 시작해 이상한 곳만 손보면 된다. 맨손 리깅보다 몇 배 빠르다
- **Mixamo**: 모델 업로드 → 자동 리깅 + 애니메이션 라이브러리.
  모델은 본인 것이고 동작만 빌리는 것이므로 나중에 직접 만든 애니메이션으로 교체 가능

**현실적 기대치**: 첫 캐릭터는 주말 작업 기준 1~3개월. 그리고 **첫 캐릭터는 버리게 될 확률이 높다.**
그게 정상이고 그 과정 자체가 학습이다.

### ⚠️ 커스터마이징은 베이스 설계 시점에 정해진다

의상 시스템을 직접 만들 것이므로, 베이스 바디를 만드는 순간 이미 그 구조를 정하는 것이다.
"나중에 추가"가 아니다.

- 의상은 **별도 메시**로 같은 아마추어에 바인딩 (바디에 붙이는 게 아님)
- 의상이 덮는 부분의 **바디 정점을 숨기는 처리** 필요 — 안 하면 옷 사이로 몸이 뚫고 나옴
- 상의/하의/신발의 **경계를 어디서 자를지**를 베이스 제작 시점에 미리 정할 것

### 병행 전략 — 캐릭터 제작이 코드를 막지 않도록

```
Blender 트랙 (몇 달)              코드 트랙 (계속 진행)
──────────────────────────────────────────────────────
캐릭터 모델링 → 리깅 → 애니메이션    3인칭 컨트롤러, 카메라 충돌
                                    오디오 리스너 방향
                                    톤매핑·안개·대기 원근
                                    지형
        ↓ 완성되면
        모델 경로만 교체
```

컨트롤러·카메라·오디오는 캐릭터 모델과 무관하게 개발된다.
모델 교체 시 코드 변경이 최소(경로만 변경)라는 점은 playground에서 이미 검증됨.

### 커스터마이징 시스템 (2단계 이후)

미리 조합을 렌더해두는 게 아니라 **런타임 레이어드 시스템**:

```
베이스 캐릭터 (skeleton)
    ├── 머리카락 메시 (같은 skeleton 공유)
    ├── 상의 메시 (같은 skeleton 공유)
    ├── 하의 메시 (같은 skeleton 공유)
    └── 소품 메시 (본에 attach)
```

- 모든 의상은 베이스 캐릭터와 **동일한 리그 구조**로 제작
- 유저 구매 아이템은 DB에 저장 → 로그인 시 불러와서 장착

### 프록시 에셋 사용 시 주의
자체 캐릭터가 완성되기 전까지 쓰는 임시 에셋도 **라이선스를 확인할 것**.
개발 중 로컬 사용은 대체로 문제없지만, 배포하는 빌드에 포함되면 조건이 달라진다.
- 상업적 사용 허가 / 수정 허가 / 재배포 허가
- 참고용으로 리그 구조를 뜯어보는 것은 대부분 허용되나, 그 리그를 그대로 베끼는 것은 별개 문제

> ⚠️ 베이스 캐릭터가 확정되면 모든 의상이 그 리그 기준으로 만들어지므로,
> **베이스 캐릭터 선택이 가장 중요한 결정**
