# Product vision and principles

Sheem (쉼, rest) is a browser-first social 3D ASMR world: a place to explore slowly, listen closely, and quietly share an environment with other people.

The first visit should feel like: **visit sheem.ai → click Enter/Play → put on headphones → enter a world**. Headphones are recommended, not mandatory. No mandatory signup, nickname form, tutorial sequence, microphone permission, or account creation should block entry. Loading and recoverable failures must be understandable.

## Principles

1. **Audio defines place.** Position, view direction, distance, shelter, and obstructions should audibly matter. A cabin doorway should be recognizable with eyes closed.
2. **Simple forms, strong atmosphere.** Aim for roughly Roblox-level geometry and readable humanoid characters, enhanced by lighting, weather, fog, materials, and particles. This supersedes the old Zelda-level visual target.
3. **Quiet presence is multiplayer's first job.** Seeing another person stop at the same campfire is enough. Voice, chat, competition, progression, and economies are not needed to prove the experience.
4. **Entry and comfort beat feature count.** Provide obvious movement help, a reachable mute/volume control, calm motion, and predictable sound levels. Speakers and lower graphical settings should remain usable.
5. **Build one place worth staying in.** Start with a compact rain clearing, a shelter, a stream, and a campfire rather than a large empty world or a world editor.
6. **Reuse what works.** Evolve the existing browser stack and prototypes. Custom character art can develop alongside the product; a finished wardrobe must not block testing.
7. **Make progress observable.** For each meaningful milestone ask, “Can this become a compelling YouTube Short?” Support work may contribute to the next demo instead of forcing a standalone video.

## Feedback loop

Build → local test → record a compelling 15–30 second demo → publish → ask viewers what should be added next → collect real feedback → prioritize → build again.

Publication is a human release step, not an instruction for agents to post. Value specific reports (“rain still sounds outside when I enter”) and repeated environment requests more than raw view counts. Preserve the calm product direction when a request would introduce noisy or expensive systems.

## What success should reveal

Can a first-time guest enter without help, move comfortably, hear a clear spatial difference, and want to pause somewhere? Do other players make that pause feel more welcoming? Can a viewer understand one improvement within 30 seconds? Use these questions before investing in additional worlds or monetization.

Initial implementation is desktop-browser focused because all current controls are keyboard/mouse. Mobile viewers should eventually get an honest compatibility message; touch controls and mobile performance are a later measured milestone, not an implied MVP promise. See [MVP scope](mvp-scope.md).
